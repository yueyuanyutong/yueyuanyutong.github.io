同一个会话挂在 QQ 和网页两端，会发生什么
踩坑记录 · 计算机 / 踩坑 · 2026-10-17

症状

三件事同时发生，看起来像三个 bug，其实是同一个：

  1. 选项框弹不出来：在网页端让我「选一个方案」，界面一直显示「思考中」，
    等了七八分钟，最后只收到一句 Error: [object Object]。
  2. 文件只到一半：我写到临时目录的排查脚本，QQ 里自动收到了一份，
    网页端却什么都没有。
  3. 消息变两份：同一句话在聊天里重复出现，或者网页这边刚发的内容「被顶掉了」。

现场（从日志读出来的时间线）

时刻 发生了什么
15:16:56 我发出的选项提问被投递到 QQ（长度 438）→ 会话进入等待，网页端没有任何提示
15:24:08 在网页端又发了一条消息 → 当前回合被中断（aborted）
15:24:08.811 同一秒，工具结果写进转录：Error: [object Object]
15:24:09 新回合照常开始，交流继续

所以它不会永久卡死，但会白等一次、并且丢掉真正的失败原因。

根因：三层叠在一起

1. 会话身份是「IM 会话」，提问通道被机器人接管

这个会话的 ID 形如 im:qq_...，从创建那一刻起，
IM 插件（@michengai/dsh-im-connect）就在启动日志里写明了
「已接管 userQuestions service 的 IM 会话」。

后果：提问只会被投递到 QQ，网页界面永远不会弹出选项控件；
而提问工具的旧模式没有超时——于是网页这边等用户、用户那边在等网页，双方互等。

2. 运行中从另一端发消息 = 排队 / 顶掉 / 中断

回合运行期间，另一端发来的消息不会「插进去」：

  • 默认当作排队消息，等当前这轮结束再处理；
  • 网页端再发一条，会把前一条顶掉（splice target=next-step），
    并中断当前步骤。

中断信号在插件里是裸对象直接抛出的（signal.reason，一个普通对象，
既不是 Error，也没有 message 字段）。框架的错误渲染只认 Error.message，
其余一律 String(obj) → 于是屏幕上只剩 [object Object]，真实原因被吃掉。

日志里还反复出现「助手消息为空」「忽略重复助手消息」，
说明网关侧另有一轮重复注入的噪音——这就是消息变两份的来源。

3. 文件推送是单通道行为

插件在回合结束时，会把 write / edit 写出的文件自动推送到 IM 聊天，
而且不过滤路径与类型——临时目录里的草稿脚本照样推。
网页端只在显式「呈现」时出附件卡片，不会自动同步。

处置与规避

  • 最省事的规矩：同一个会话不要同时挂在两个客户端上。
    这不是「多端同步」，而是竞态——谁在什么时候拥有控制权，插件没有统一仲裁。
  • 电脑上干活时就把 QQ 那条会话放一边；要用 QQ 就只用 QQ。
  • 临时脚本改用命令行内联写入，别用会触发文件推送的写文件方式。
  • 已经卡住了：在 QQ 里直接回文字或数字作答（提问挂起期间，该会话任何不以 / 开头的文字都会被当成答案，
    不会变成新任务），或者发 /stop 跳出。

QQ 侧的手动闸门（功能一直有）

在 QQ 私聊里直接发这些命令即可，不需要改任何配置：

命令 作用
/stop 真正中断当前运行，排队消息保留，停下后直接发消息即可续聊
/steer 补充要求 运行中插入补充指令，边跑边改需求，不打断本轮
/status 查看运行中 / 空闲（会附带一个「停止任务」按钮）
/queue 查看排队消息；可 remove / edit / steer <消息ID>（把排队消息转成补充指令）
/help 全部命令

其余常用：/new（/clear）新开会话、/sessions 接续旧会话、/history 最近记录、
/model /reasoning /presets 查看与切换模型、推理等级、Agent 预设、
/fork 分叉、/rename 改名、/delivery 交付记录、/unbind /mute 解除绑定与静音。

教训

  1. 「多端在线」不等于「多端同步」：一个会话同时被两个客户端操作时，
    消息去哪、谁有控制权、失败算谁的，都需要明确的仲裁规则；没有规则就是竞态。
  2. 别只信界面上的错误文本：String(非 Error 对象) 会把真因压成 [object Object]。
    遇到这种没有信息量的报错，要去翻原始转录与网关日志，那里才有完整的中断原因。
  3. 自动推送类的功能要看它推什么、推给谁：不过滤路径与类型的文件推送，
    会把临时草稿也送到聊天窗口里。
